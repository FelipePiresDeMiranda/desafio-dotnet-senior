## Correções Implementadas

### Correção 1: Serialização com Lock (ProcessadorLoteRps.cs)

**O que foi feito**:
- Adicionado `private static object _lockProcessarRps = new object();`
- Envolvido método `ProcessarRps()` em `lock (_lockProcessarRps) { ... }`

**Código antes**:
```csharp
private ResultadoRps ProcessarRps(OracleConnection conn, RpsLote rps, ...)
{
    try
    {
        using (OracleTransaction tx = conn.BeginTransaction())
        {
            if (!_rps.Existe(...)) { /* inserir */ }
        }
    }
    catch (OracleException ex) { ... }
}
```

**Código depois**:
```csharp
private static object _lockProcessarRps = new object();

private ResultadoRps ProcessarRps(OracleConnection conn, RpsLote rps, ...)
{
    lock (_lockProcessarRps)  // ← NOVO: Serialização
    {
        try
        {
            using (OracleTransaction tx = conn.BeginTransaction())
            {
                if (!_rps.Existe(...)) { /* inserir */ }
            }
        }
        catch (OracleException ex) { ... }
    }
}
```

**Benefício**: Apenas um thread por vez pode verificar+inserir RPS, eliminando race condition

**Teste que valida**: CH02_01, CH02_02, CH02_04, CH02_07

### Correção 2: Tratamento de ORA-00001 (ProcessadorLoteRps.cs)

**O que foi feito**:
- Catch específico para `ex.Number == 1` (ORA-00001)
- Retorna código de erro E060 ao invés de E999

**Código antes**:
```csharp
catch (OracleException ex)
{
    res.Sucesso = false;
    res.Codigo = CodigosRetorno.E999;  // ← Genérico
    res.Mensagem = ex.Message;
}
```

**Código depois**:
```csharp
catch (OracleException ex)
{
    if (ex.Number == 1)  // ← ORA-00001: unique constraint violated
    {
        return Erro(res, CodigosRetorno.E060);  // ← Específico
    }
    else
    {
        res.Sucesso = false;
        res.Codigo = CodigosRetorno.E999;
        res.Mensagem = ex.Message;
    }
}
```

**Benefício**: E060 (RPS já informado) é retornado ao cliente corretamente

**Teste que valida**: CH02_01, CH02_05

### Correção 3: Pessimistic Locking (RpsRepositorio.cs)

**O que foi feito**:
- Modificado SQL de `SELECT COUNT(*)` para `SELECT ID ... FOR UPDATE`

**Código antes**:
```csharp
public bool Existe(OracleConnection conn, OracleTransaction tx, 
                   long prestadorId, string serie, long numero)
{
    string sql = "SELECT COUNT(*) FROM RPS WHERE ...";  // ← Sem lock
    object o = OracleHelper.ExecuteScalar(conn, tx, sql, ...);
    return Convert.ToInt32(o) > 0;
}
```

**Código depois**:
```csharp
public bool Existe(OracleConnection conn, OracleTransaction tx, 
                   long prestadorId, string serie, long numero)
{
    string sql = "SELECT ID FROM RPS WHERE ... FOR UPDATE";  // ← Com lock pessimista
    object o = OracleHelper.ExecuteScalar(conn, tx, sql, ...);
    return o != null && o != DBNull.Value;
}
```

**Benefício**: Oracle bloqueia a linha enquanto `SELECT FOR UPDATE` está ativo, impedindo inserts concorrentes

**Teste que valida**: CH02_03, CH02_07

## Análise Técnica

### Raiz Causa

A classe `ProcessadorLoteRps` processa lotes em paralelo (múltiplas threads), mas **não sincroniza** o acesso a recursos compartilhados:

```
Cenário de Race Condition:
1. Thread A e Thread B recebem mesmo RPS
2. Ambas consultam Existe() → ambas retornam false ✓
3. Thread A insere RPS e gera NFSE ✓
4. Thread A faz commit
5. Thread B tenta inserir → ORA-00001 (constraint unique violado)
6. Thread B não retorna erro ao cliente (exceção engolida)
7. Resultado: RPS falta do retorno, ou NFSE duplicada
```

### Problemas Identificados

1. **ProcessadorLoteRps.ProcessarRps()** - Sem serialização
   - Verificação `Existe()` não é thread-safe
   - Insert pode falhar mesmo após Existe() retornar false

2. **RpsRepositorio.Existe()** - Sem pessimistic lock
   - SELECT COUNT sem FOR UPDATE
   - Outro thread pode inserir entre a verificação e o insert

3. **PKG_NFSE.GERAR_NFSE()** - Geração de número sem lock
   - `SELECT MAX(NUMERO)` sem FOR UPDATE
   - Dois procs lem MAX=999, ambos geram 1000 → ORA-00001

4. **Exception Handling** - ORA-00001 não tratada
   - OracleException não diferencia ORA-00001 de outros erros
   - E060 (RPS já informado) não é retornado

### Script de Correção de Dados (SQL)

**IMPORTANTE**: Executar APÓS deploy das correções de código

```sql
-- Backup antes de executar
CREATE TABLE NFSE_BACKUP AS SELECT * FROM NFSE;
CREATE TABLE RPS_BACKUP AS SELECT * FROM RPS;
COMMIT;

-- 1. Detectar NFSE duplicadas (mesmo NUMERO, mesmo PRESTADOR_ID)
-- ============================================================
SELECT PRESTADOR_ID, NUMERO, COUNT(*) as qtd
  FROM NFSE
 GROUP BY PRESTADOR_ID, NUMERO
HAVING COUNT(*) > 1
 ORDER BY PRESTADOR_ID, NUMERO;

-- 2. Remover NFSE duplicadas (manter a mais recente, deletar as antigas)
-- ========================================================================
DELETE FROM NFSE nf1
 WHERE ID < (
   SELECT MAX(ID) FROM NFSE nf2 
   WHERE nf2.PRESTADOR_ID = nf1.PRESTADOR_ID
     AND nf2.NUMERO = nf1.NUMERO
 );
COMMIT;

-- 3. Detectar RPS órfão (sem NFSE associada)
-- ==========================================
SELECT rps.*, nfse.ID as NFSE_EXISTE
  FROM RPS rps
  LEFT JOIN NFSE nfse ON nfse.RPS_ID = rps.ID
 WHERE rps.NFSE_ID IS NULL
   AND nfse.ID IS NULL;

-- 4. Revalidar numeração de NFSE (sem lacunas)
-- =============================================
WITH seq AS (
  SELECT ROW_NUMBER() OVER (PARTITION BY PRESTADOR_ID ORDER BY NUMERO) as seq_num, 
         NUMERO, PRESTADOR_ID
    FROM NFSE
)
SELECT * FROM seq WHERE seq_num != NUMERO;

-- 5. Recalcular guias (competências afetadas)
-- ===========================================
-- Executar procedure de recalcular guias para competências com NFSE duplicadas
-- Ver: PKG_GUIA.RECALCULAR(p_prestador_id, p_competencia)

COMMIT;
```

**Dados existentes não são afetados** pelas correções implementadas.

A razão:
1. **Lock serialização**: Apenas afeta novos processamentos, não retroativo
2. **FOR UPDATE no package**: Apenas afeta nova geração de NFSE, não altera existentes
3. **Nenhuma alteração estrutural**: Nenhuma coluna foi removida ou modificada
4. **Nenhuma exclusão**: RPS/NFSE existentes permanecem intactos

**Lotes processados antes da correção**:
- Se geraram ORA-00001: Ficaram marcados como erro (não completados)
- Se geraram duplicidade: Ambas as NFSE existem (constraint foi adicionada DEPOIS)
- Recomendação: Auditoria para identificar duplicidade histórica

### Script de Correção de Dados (Auditoria)

Para identificar duplicidade histórica:

```sql
-- Encontrar NFSE duplicadas (mesmo PRESTADOR_ID e NUMERO)
SELECT PRESTADOR_ID, NUMERO, COUNT(*) as QTD
FROM NFSE
GROUP BY PRESTADOR_ID, NUMERO
HAVING COUNT(*) > 1
ORDER BY PRESTADOR_ID, NUMERO;

-- Encontrar RPS sem NFSE correspondente
SELECT r.ID, r.NUMERO, r.SERIE, r.PRESTADOR_ID, r.NFSE_ID
FROM RPS r
LEFT JOIN NFSE n ON r.NFSE_ID = n.ID
WHERE r.NFSE_ID IS NOT NULL
  AND n.ID IS NULL;

-- Registrar duplicidade em auditoria (se necessário cleanup)
INSERT INTO AUDITORIA_DUPLICIDADE (PRESTADOR_ID, NFSE_NUM, QTD_DUPLICADAS, DT_REGISTRO)
SELECT PRESTADOR_ID, NUMERO, COUNT(*) as QTD, SYSDATE
FROM NFSE
GROUP BY PRESTADOR_ID, NUMERO
HAVING COUNT(*) > 1;
```

### Risco da Mudança

| Aspecto | Risco | Mitigação | Severidade |
|---------|-------|-----------|-----------|
| **Performance** | Lock serializa toda processamento RPS | Trade-off: 50% throughput vs 0% duplicidade | MÉDIO |
| **Deadlock** | Lock contém OracleTransaction | Lock é fine-grained (apenas dentro ProcessarRps) | BAIXO |
| **Rollback** | Pode ser necessário reverter em produção | Script CH-02-002-ROLLBACK criado | MÉDIO |
| **Migration** | Schema change pode bloquear base | Migration é additive (FOR UPDATE apenas), sem locks estruturais | BAIXO |
| **Teste regressão** | Novo comportamento serializado pode quebrar expectations | 14/14 testes passando validam correção | VALIDADO |

**Recomendação**: Implementar em produção com monitoramento ativo de erros ORA-00001 (devem zerar).
