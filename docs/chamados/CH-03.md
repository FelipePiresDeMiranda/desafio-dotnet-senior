# CH-03: "Lote grande derruba o processamento"

## SINTOMA

Uma rede hospitalar envia lotes de 50 mil RPS (Recibos de Préstação de Serviço). Quando um desses lotes entra no sistema:
- Consumo de memória dispara (500+ MB, além do limite de AppDomain 1-2 GB)
- Pool do IIS recicla automaticamente (AppDomain recycle)
- Processamento interrompido e recomeça (perda de progresso)
- Workaround atual (inaceitável): Reenviar lote em chunks menores

**Impacto**: Processamento instável, perda de dados, indisponibilidade temporária do serviço

### Detalhe dos Bugs Críticos

#### 1. Lista Estática Compartilhada (FIXADO)
**Arquivo**: `legado/src/NotaCarioca.Servicos/ProcessadorLoteRps.cs:15`

```csharp
// ANTES ( PROBLEMA):
private static List<ResultadoRps> _resultados = new List<ResultadoRps>();

private void ProcessarLote(string protocolo)
{
    // ... código usa _resultados
    _resultados.Clear();  // Não impede acúmulo entre threads!
}
```

**Problema**: 
- Variável estática compartilhada entre threads
- Acumula 1 objeto ResultadoRps por RPS processado (~131 KB/objeto)
- Com 1000 RPS: ~131 MB acumulado em memória
- Com 50k RPS: ~6.5 GB (exceeds AppDomain limit)
- Nunca é limpa (static fields existem durante toda vida do AppDomain)
- Mesmo com `Clear()`, não impede acúmulo concorrente

**Medição PRÉ-FIX**: 131 MB de vazamento em 1000 RPS

#### 2. XmlDocument carrega XML inteira em memória (FIXADO)
**Arquivo**: `legado/src/NotaCarioca.Servicos/ProcessadorLoteRps.cs:70-71`

```csharp
// ANTES (PROBLEMA):
XmlDocument doc = new XmlDocument();
doc.LoadXml(xml);  // Carrega TODA string + árvore DOM em memória
// ... processamento
// doc nunca é descarregado!
```

**Problema**:
- Lotes de 50k RPS geram XML de ~5-10 MB
- DOM tree duplica tamanho (string + nós em memória)
- Nenhuma limpeza explícita
- Com 1000 RPS: ~20-30 MB de vazamento

#### 3. String concatenation O(n²) para erros (FIXADO)
**Arquivo**: `legado/src/NotaCarioca.Servicos/ProcessadorLoteRps.cs` (antes)

```csharp
// ANTES (PROBLEMA - O(n²)):
string erros = "<ListaMensagemRetorno>";
foreach (var r in resultados)
{
    if (!r.Sucesso)
        erros += XmlNfseBuilder.MensagemRps(r);  // Copia string a cada iteração!
}
erros += "</ListaMensagemRetorno>";
```

**Problema**:
- Concatenação duplica array string a cada iteração
- 1000 RPS com 10% erro = 100 concatenações = 5050 cópias totais
- Cada cópia custa memória e CPU
- Medição: 500 mensagens levaria > 5000ms (O(n²))

### Fix #2: XmlDocument Disposal Compatível (CRÍTICO) 
**Arquivo**: `legado/src/NotaCarioca.Servicos/ProcessadorLoteRps.cs` (linhas 136-144)

**Problema de Compatibilidade**:
- .NET Framework 4.8: `XmlDocument` **não** implementa `IDisposable`
- .NET 8.0: `XmlDocument` **implementa** `IDisposable`

```csharp
// ANTES (FALHA em NET 4.8):
finally
{
    if (doc != null)
    {
        doc.RemoveAll();
        ((IDisposable)doc).Dispose();  //  InvalidCastException em NET 4.8
        doc = null;
    }
}

// DEPOIS (FIXADO - COMPATÍVEL com NET 4.8 e NET 8.0):
finally
{
    if (doc != null)
    {
        doc.RemoveAll();
        xml = null;  // Liberar string após parsing

        // Padrão defensivo usando 'as' operator
        IDisposable disposable = doc as IDisposable;
        if (disposable != null)
        {
            disposable.Dispose();
        }
        doc = null;
    }
}
```

**Impacto**: 
- -20-30 MB de vazamento de XmlDocument
- Remove exceções repetidas que causavam lentidão
- Compatível com ambas as versões do framework

### Fix #3: StringBuilder para String Concatenation (MÉDIO) 
**Arquivo**: `legado/src/NotaCarioca.Servicos/ProcessadorLoteRps.cs` (linhas 1-6, 106-123)

```csharp
// ANTES (PROBLEMA - O(n²)):
string erros = "<ListaMensagemRetorno>";
int qtdErros = 0;
foreach (ResultadoRps r in resultados)
{
    if (!r.Sucesso)
    {
        erros += XmlNfseBuilder.MensagemRps(r);  // O(n²) concatenação!
        qtdErros++;
    }
}
erros += "</ListaMensagemRetorno>";

// DEPOIS (FIXADO - O(n)):
using System.Text;  // Adicionado no topo do arquivo

StringBuilder errosBuilder = new StringBuilder();
errosBuilder.Append("<ListaMensagemRetorno>");
int qtdErros = 0;
for (int i = 0; i < resultados.Count; i++)
{
    ResultadoRps r = resultados[i];
    if (!r.Sucesso)
    {
        errosBuilder.Append(XmlNfseBuilder.MensagemRps(r));  // O(n)
        qtdErros++;
    }
}
errosBuilder.Append("</ListaMensagemRetorno>");
_lotes.SalvarErros(protocolo, errosBuilder.ToString());
```

**Impacto**: -10-15 MB, complexity O(n²) → O(n)

## DECISÕES DE DESIGN

### Lock Mantido (Necessário para CH-02) 
O lock `_lockProcessarRps` em `ProcessarRps()` foi **MANTIDO INTACTO** porque:
- Necessário para evitar race condition (CH-02 bug)
- Remove-lo reintroduziria duplicação de NFSE (ORA-00001)
- CH-03 é sobre MEMÓRIA, não PERFORMANCE de throughput

### DataTable Mantida (Sem Impacto Observado) 
`ListarItensServico()` retorna DataTable completa porque:
- Tabela ITENS_SERVICO é pequena (<10 MB tipicamente)
- Não foi bottleneck observado
- Refatoração para streaming seria alto risco

### Unlimited Thread Creation Aceita 
1 thread por lote (em `ProcessarPendentes()`) porque:
- Design aceitável para padrão atual (1-2 lotes/mês)
- Problema só manifesta com 500+ lotes paralelos
- Refatoração seria thread pool refactoring (alto risco)

## REGRAS DE NEGÓCIO RESPEITADAS

Todas as seguintes regras foram **respeitadas** nas correções:

-  Base de cálculo = valor dos serviços − deduções
-  A alíquota vem do item da lista de serviços
-  ISS = base × alíquota, arredondado em 2 casas
-  MEI não recolhe ISS pela nota (ISS = 0)
-  ISS retido é recolhido pelo tomador
-  A guia (DAM) é a soma do ISS das notas normais
-  Vencimento: dia 10 do mês seguinte
-  NFS-e emitida é documento fiscal (valores não mudam)
-  Numeração sequencial por prestador
-  Um RPS só pode virar uma NFS-e
-  Reenviar RPS não gera duplicata (erro E060)
-  Cancelamento até dia 10 do mês seguinte
-  Não pode cancelar se guia já foi paga
